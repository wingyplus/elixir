# Where does `make compile` spend its time?

Profiled elixir-lang/elixir@eaa0e70 (1.21.0-dev) on Erlang/OTP 28.4 (JIT) on a
4 vCPU Xeon @ 2.10GHz VM. A full `make clean && make compile` takes **~62 s**
(see `results/`).

## 1. Phase breakdown

Each step of the Makefile timed on its own (`real` = wall time, `user` = CPU time):

| Phase | Wall | CPU (user) | Parallel? |
|---|---:|---:|---|
| yecc: `elixir_parser.yrl` → `.erl` | 2.3 s | 2.2 s | no |
| `erl -make`: 33 Erlang files in `lib/elixir/src` | 10.7 s | 10.1 s | **no** |
| bootstrap: `elixir_compiler:bootstrap` (~50 core `.ex` files) | 20.5 s | 20.1 s | **no** |
| unicode: 3 separate `elixirc` runs | 7.1 s | 6.9 s | **no** |
| stdlib: `elixirc lib/**/*.ex` | 9.2 s | 25.6 s | yes (~2.8x) |
| `infer.exs` + app generation | 2.3 s | | partly |
| eex, mix, ex_unit, logger, eex, iex (one after another) | ~10.7 s | | within each app only |

**~41 s of the ~62 s (about 2/3) runs on a single core**, so on the 4-core box
most of the CPU sits idle during the bootstrap phases.

## 2. Inside the phases: the Erlang compiler backend dominates

`perf record -g` with `+JPperf true` (JIT symbols + frame pointers), inclusive time:

| Bucket | Bootstrap | stdlib `elixirc` |
|---|---:|---:|
| `compile:internal_comp` (Erlang compiler, all passes) | 58% | 60% |
| ↳ `beam_ssa_opt` (SSA optimizer) | 36% | 35% |
| ↳ `beam_validator` | 6% | 5% |
| ↳ `beam_ssa_pre_codegen` | 6% | 6% |
| `Module.Types` (Elixir type checker / inference) | n/a | ~6% |
| `elixir_expand` (macro expansion) | 2% | 2% |
| `elixir_tokenizer` + parser | <1% | <1% |
| garbage collection | 16% | 15% |

Inside `beam_ssa_opt` the cost is spread out: `ssa_opt_type_start`/signatures
~6%, `ssa_opt_type_continue` ~6%, `ssa_opt_alias` ~4.5%, `ssa_opt_live` ~4%,
`ssa_opt_dead` ~3.5%, `ssa_opt_sink` ~3%. No single pass is the culprit.

Elixir's own front end (tokenizing, parsing, expanding) costs little. Most of
the time goes to turning Erlang abstract code into BEAM with `compile:forms`.

Raw data: `profile/perf_bootstrap_top.txt`, `profile/perf_stdlib_top.txt`.

| File | Time | Notes |
|---|---:|---|
| `base.ex` | 2.9 s | macro-generated binary-matching clauses; `ssa_opt_type_start` 0.6 s, `beam_ssa_bsm` 0.2 s |

`Calendar` and `Calendar.ISO` depend on each other: each waits ~7–8 s until
deadlock resolution, so they are the last two files compiled. Because all four
cores stay busy in the meantime, this costs only ~0.5 s of tail.

Raw data: `profile/stdlib_profile_time.txt`.

## 4. Experiments: what could be faster

| Change | Before | After | Saving |
|---|---:|---:|---:|
| Compile the bootstrap modules with the SSA optimizer off (`ERL_COMPILER_OPTIONS='[no_ssa_opt,no_bool_opt,no_share_opt,no_bsm_opt,no_recv_opt,no_throw_opt]'` on just the bootstrap command) | 61.8 s | 54.3 s | **−7.5 s (−12%)** full `make compile` (hyperfine, 3 runs) |
| Compile `lib/elixir/src/*.erl` in parallel in one VM (parser first) instead of `erl -make` | 10.7 s | 7.0 s | −3.7 s (bounded by `elixir_parser.erl`) |
| Compile the 3 unicode files in one `elixirc` call instead of three | 7.4 s | 4.1 s | −3.3 s |

The bootstrap `.beam`s are throwaway: the stdlib is recompiled immediately
afterwards with full optimizations. Turning the optimizer off for bootstrap
therefore produced the same final `.beam` files. The only 3 files that
differed (`IEx`, `IEx.Helpers`, `Mix.Tasks.New`) also differ between two
ordinary default builds.

These three changes don't overlap much, so together they could take roughly
10–14 s (~20%) off a clean build on this machine.
